
# Hasamex Expert Call Analyzer — Technical Case Study

A small app that analyzes 3 expert-call transcripts (France Germany / UK, robotic
surgery market) and: answers an interview guide per expert, extracts exact
quotes with timestamps, synthesizes cross-transcript themes and disagreements,
and answers free-form questions across all transcripts — all with grounded,
verifiable citations and no invented facts.

## 1. Quick start

```bash
cd hasamex_case
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
export GROQ_API_KEY=gsk_...
streamlit run app.py
```

Get a free key at [console.groq.com/keys](https://console.groq.com/keys).

Opens at `http://localhost:8501`. Four tabs: Interview Guide, Themes &
Disagreements, Ask a Question, Browse Transcripts.

## 2. Architecture

```
Transcript_*.txt ──▶ parser.py ──▶ list[Turn]  (speaker, timestamp, text, market...)
                                        │
                                        ▼
                                retrieval.py (TF-IDF over turns)
                                        │
                         ┌──────────────┼───────────────┐
                         ▼              ▼                ▼
              per-transcript index   global index    (interview guide
              (guide Q&A)            (chat Q&A)        questions parsed
                         │              │               from Interview_Guide.txt)
                         ▼              ▼
                     pipeline.py — llm_client.py (Groq/Llama, JSON-only output)
                         │
                         ▼
              quote validation (exact substring check against source Turn)
                         │
                         ▼
                    app.py (Streamlit UI)
```

**`src/parser.py`** — turns each `.txt` transcript into a list of `Turn`
objects: `{transcript_id, expert_name, role, market, turn_index, timestamp,
speaker, text, is_interviewer}`. This structured form is the backbone of
the whole app — every timestamp and quote shown later is read from here,
never generated by the model.

**`src/retrieval.py`** — TF-IDF + cosine similarity over turns, one index
per transcript (for guide Q&A) and one global index across all three (for
chat). A retrieval unit is always an **expert's answer turn**, but its
search text is *"preceding interviewer question + the answer"* — this
fixes a real failure mode where a query like "what are the barriers?"
lexically matches the interviewer's question turn better than the expert's
actual answer, which is the one that should be cited.

**`src/llm_client.py`** — thin Groq API wrapper that forces
JSON-only output and strips stray markdown fences.

**`src/pipeline.py`** — the grounding pattern used everywhere in this app:

1. Retrieve the top-k relevant turns for a question.
2. Ask the model for `{answer, quotes: [{ref, quote}], insufficient_evidence}` —
   the model may only *select* a `ref` (an excerpt number) and copy a
   substring from it. It is explicitly told never to combine text across
   excerpts or paraphrase inside a quote.
3. **Validate every quote in code**: check it's an exact (whitespace-normalized)
   substring of the turn text it claims to cite. Any quote that fails this
   check is silently dropped — it never reaches the UI.
4. Attach `timestamp`, `speaker`, `market` from the `Turn` object — the
   model is never asked for a timestamp, so it cannot invent one.

This same pattern powers all three AI features:
- `answer_guide_question()` — one expert, one interview-guide question.
- `answer_chat_question()` — free-form question, retrieval across all 3 transcripts.
- `synthesize_theme()` — takes the three (already grounded, already-verified)
  per-expert answers + quotes for one guide question, and asks the model to
  compare them into common themes and disagreements. Because the input to
  this step is already-verified material, the synthesis step can't smuggle
  in a fabricated fact even if it wanted to — it's reasoning over verified
  quotes, not raw transcript text.

## 3. How this maps to the case requirements

| Requirement | Implementation |
|---|---|
| Upload/read 3 transcripts | `parser.py`, loaded in `app.py` |
| Answer interview-guide questions per expert | Tab 1, `answer_guide_question()` |
| Extract exact quotes | Quotes are LLM-selected `ref`s, verified as exact substrings before display |
| Show source timestamp | Attached from `Turn.timestamp` in code, not model output |
| Identify themes & disagreements | Tab 2, `synthesize_theme()` |
| Ask questions across all transcripts | Tab 3, `answer_chat_question()` over the global index |
| Do not invent information | `insufficient_evidence` flag + substring-validated quotes + "answer only from excerpts" system prompts |

## 4. Model choice

Uses Groq's hosted inference (`llama-3.3-70b-versatile` by default, overridable
via `HASAMEX_MODEL`) via the OpenAI-compatible `groq` Python SDK, with native
JSON mode (`response_format={"type": "json_object"}`) enforcing structured
output. This is a synthesis/comparison task over short text (not a coding or
massive-context task), so a fast, cheap, strong-at-instruction-following model
is the right tradeoff — Groq's LPU inference is also noticeably faster than a
typical API call, which matters here since the guide-QA tab fires one call
per expert per question. Swapping providers only touches `src/llm_client.py`;
`pipeline.py` and everything above it is provider-agnostic (it only calls
`call_json(system_prompt, user_prompt)` and gets a dict back).

## 5. How hallucinations are reduced (the main engineering decision)

Three layers, from most to least mechanical:

1. **Timestamps are never generated.** They're a field on a `Turn` object,
   attached in code by index — there's no path for the model to invent one.
2. **Quotes are verified, not trusted.** The model can only reference an
   excerpt number and copy from it; every returned quote is checked with
   an exact substring match against the real transcript text before it's
   shown. Anything that fails is dropped rather than "fixed" or shown anyway.
3. **Retrieval scopes what the model can see.** The model is given only the
   top-k relevant turns, told explicitly to answer *only* from them, and
   can flag `insufficient_evidence` rather than guessing when the transcript
   doesn't address a question.

What this does *not* fully solve: the free-text `answer` field (the
model's own summary) is not substring-verified, since it's meant to be a
paraphrase. That's why every answer is shown next to its verified quotes —
the quotes are the ground truth; the paraphrase is there for readability.
A next step for a production version would be an automatic
entailment/consistency check between the `answer` and its `quotes`.

## 6. Limitations (honest, given "not production-ready" scope)

- Retrieval is TF-IDF, not semantic embeddings — works well at this corpus
  size (3 transcripts, ~14 turns each) but would need to be swapped out at scale.
- No persistence — everything is recomputed per Streamlit session (cached
  with `st.cache_resource` for parsing/indexing only, not for LLM calls).
- Interviewer turns are excluded from quoting by design (only expert
  statements are treated as citable "quotes") — a deliberate simplification,
  worth confirming with stakeholders if interviewer framing ever matters.
- Transcript parsing assumes the exact `MM:SS` / `Speaker: text` format
  given in the case pack; a real pipeline would need a more robust
  ingestion step for arbitrary transcript exports (Otter.ai, Rev, Zoom, etc).

## 7. Scaling from 3 transcripts to 30+

- **Retrieval**: replace TF-IDF with real embeddings (e.g. a small
  embedding model) + a vector store (pgvector/FAISS/Chroma), chunked by
  turn or small turn-windows, metadata-filtered by market/role.
- **Cost/latency**: guide Q&A is currently one LLM call per (expert × guide
  question) — fine at 3×6, but at 30 transcripts that's 30× the calls.
  Batch multiple questions into a single call per transcript (one call,
  multiple JSON answers), and cache aggressively since transcripts don't change.
- **Synthesis at scale**: comparing 30 experts' answers directly in one
  prompt won't fit context. Do it hierarchically — cluster/summarize in
  batches of ~5-8 experts, then synthesize the batch summaries — same
  grounding discipline (quotes-only inputs) at each level.
- **Storage**: move from in-memory parsing to a proper ingestion pipeline —
  parse once, persist structured turns + embeddings in a DB, don't
  re-parse/re-embed on every run.
- **UI**: add filtering (by market, role, question), pagination, and an
  export (PDF/deck) of the synthesized themes for the research team.
- **Evaluation**: with more transcripts, add an offline eval set (known
  question → known correct quote) to regression-test retrieval and
  quote-validation precision/recall as the corpus grows.
